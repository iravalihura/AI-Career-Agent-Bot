# ADR 003: Вибір архітектурного стилю системи (Модульний моноліт vs Мікросервіси)

- **Статус:** Прийнято
- **Дата:** 2026-11-27
- **Проєкт:** AI Career Agent Bot

## Контекст

Програмна система **AI Career Agent Bot** призначена для автоматизації пошуку вакансій, оцінки сумісності профілю кандидата з описом вакансії за допомогою LLM та генерації адаптованих резюме й супровідних листів через Telegram-бот.

Систему розробляє невелика команда (1 розробник) у межах навчального проєкту з обмеженими ресурсами інфраструктури та часу на розгортання. Необхідно поєднати:

- інтерактивну взаємодію з користувачами через Telegram API (час відгуку $\le 3$ с);
- періодичний фоновий збір та нормалізацію вакансій із зовнішніх платформ;
- асинхронні виклики зовнішніх LLM API та генерацію PDF-документів;
- надійне транзакційне збереження профілів користувачів, вакансій та історії відгуків.

## Розглянуті варіанти

### Порівняння архітектурних альтернатив

| Критерій                            | Модульний моноліт                                                                          | Мікросервіси                                                                                 |
| :---------------------------------- | :----------------------------------------------------------------------------------------- | :------------------------------------------------------------------------------------------- |
| **Організація коду та розгортання** | Логічно ізольовані модулі в межах одного застосунку, єдиний артефакт розгортання           | Окремі сервіси з незалежними репозиторіями/процесами розгортання та мережевою взаємодією     |
| **Складність інфраструктури**       | Низька: простіша локальна розробка, відлагодження та CI/CD                                 | Висока: потрібні окремі сервіси, міжсервісні контракти, розподілене трасування та моніторинг |
| **Узгодженість даних**              | Проста: єдина реляційна БД (PostgreSQL) і локальні транзакції                              | Складніша: розподілені транзакції, eventual consistency, дублювання або синхронізація даних  |
| **Масштабування та ізоляція збоїв** | Масштабується весь застосунок; фонові задачі ізолюються на рівні асинхронних воркерів/черг | Кожен сервіс масштабується окремо, але мережеві виклики додають точки відмови та затримки    |
| **Відповідність умовам команди**    | Оптимально для малої команди й швидких ітерацій                                            | Надмірно для 1 розробника на стартовому етапі                                                |

## Рішення

Обрано архітектурний стиль **модульного моноліту** з чітким розділенням відповідальності між внутрішніми модулями та використанням єдиної бази даних **PostgreSQL**:

1. **Модуль взаємодії з користувачем (Telegram Bot Module):** обробка команд, станів діалогу (FSM), завантаження файлів і надсилання сповіщень.
2. **Модуль моніторингу та парсингу вакансій (Vacancy Parser Module):** періодичний збір, очищення та нормалізація оголошень із зовнішніх джерел.
3. **Модуль ШІ та генерації документів (AI & Document Module):** взаємодія з LLM API, розрахунок релевантності, формування супровідних листів і PDF-резюме.
4. **Модуль доступу до даних (Data Access Module):** робота з профілями, вакансіями та історією відгуків у PostgreSQL.

## Альтернатива

**Мікросервісна архітектура** (розділення бота, парсера, ШІ-ядра та генератора PDF на окремі сервіси з внутрішніми API / брокером повідомлень).

**Причина відхилення:** за поточного розміру команди (1 розробник) та очікуваного навантаження мікросервісний підхід створює надмірну _випадкову складність_ — потребує налаштування міжсервісної автентифікації, ретраїв між сервісами, узгодження схем API та складнішого моніторингу без відчутних переваг на старті.

## Вплив вимог на структуру системи

- **Вимога продуктивності (час відгуку бота $\le 3$ с):** зумовила відокремлення фонового парсингу вакансій та тривалих викликів LLM від обробки інтерактивних команд користувача (використання асинхронних черг / фонових задач).
- **Вимога надійності та доступності ($\ge 99.9\%$):** зумовила винесення інтеграцій із зовнішніми платформами вакансій та LLM API в ізольовані модулі-адаптери з обробкою таймаутів і помилок, щоб збій зовнішнього джерела не блокував роботу бота.
- **Вимога модифікованості:** чіткі межі модулів дозволяють у майбутньому винести найбільш навантажений модуль (наприклад, парсер або AI-воркер) в окремий контейнер/сервіс без переписування бізнес-логіки.

## Наслідки

### Позитивні

- Швидкий старт розробки, простіше тестування та відлагодження в єдиному середовищі.
- Відсутність мережевих затримок і серіалізації між внутрішніми модулями.
- Просте забезпечення цілісності даних за допомогою стандартних ACID-транзакцій у PostgreSQL.
- Зменшення витрат на інфраструктуру та підтримку CI/CD.

### Негативні

- Усі модулі використовують спільні обчислювальні ресурси (CPU/RAM) в межах одного розгортання.
- Необхідна дисципліна в коді, щоб не порушувати межі між модулями та не створювати жорсткого зв’язування.

## Умова перегляду

Рішення має бути переглянуте на користь виділення окремих мікросервісів або незалежних воркерів, якщо настане хоча б одна з умов:

1. Пікове навантаження від фонового парсингу вакансій або генерації PDF/LLM-запитів почне стабільно погіршувати час відповіді Telegram-бота (p95 перевищуватиме $3$ секунди).
2. Кількість розробників у проєкті зросте до 2+ незалежних підкоманд, яким потрібні окремі цикли релізів та різні технологічні стеки для окремих компонентів.
3. Виникне потреба в незалежному горизонтальному масштабуванні парсерів під велику кількість зовнішніх джерел.
